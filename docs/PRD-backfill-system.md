# PRD: Meta 광고 데이터 백필 시스템

**작성일**: 2026-01-28
**버전**: 1.0
**상태**: Draft

---

## 1. 배경 및 현황 분석

### 1.1 현재 문제점

| 문제 | 상세 | 영향도 |
|------|------|--------|
| **데이터 소스 불일치** | `daily-backfill.yml`이 Supabase 저장 스크립트(`backfill.js`) 사용 | 🔴 Critical |
| **Airtable 백필 미작동** | GitHub Actions에 `AIRTABLE_API_KEY` secret 없음 | 🔴 Critical |
| **환율 적용 불일치** | 일부 데이터 USD, 일부 KRW (1490배 차이) | 🟡 High |
| **중복 데이터** | H.E.A 판교: 같은 date+device+campaign 레코드 중복 | 🟡 High |
| **클라이언트 분리 미흡** | `--all` 옵션 사용 시 모든 클라이언트 영향 | 🟡 High |

### 1.2 데이터 점검 결과

**H.E.A 판교 (2026년 1월)**
- 레코드 수: 72개
- 중복 발견: 같은 날짜+디바이스 데이터 중복 존재
- 지출: $429 (정상)

**나라똔 (2026년 1월)**
- 레코드 수: 60개
- 1/1~13: 리드 106건 (정상) - `202601_1월잠재고객캠페인` 운영
- 1/14~: 리드 0건 (정상) - 잠재고객 캠페인 종료, 트래픽 캠페인만 운영
- 지출 이상: 1/14 이후 환율 미적용 ($10 저장 vs $14,000 예상)

## 2. 목표

### 2.1 핵심 목표

1. **자동 백필 정상화**: 매일 새벽 3시 Airtable에 Meta 데이터 자동 백필
2. **데이터 정합성 확보**: 환율 적용, 중복 방지, 클라이언트 분리
3. **모니터링 강화**: 백필 실패/이상 감지 및 알림

### 2.2 성공 지표

| 지표 | 목표 |
|------|------|
| 백필 성공률 | 99% 이상 |
| 데이터 정합성 | 100% (환율 적용, 중복 없음) |
| 알림 응답 시간 | 백필 완료 후 1분 이내 |

## 3. 요구사항

### 3.1 기능 요구사항

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-1.1 | 매일 새벽 3시(KST) 자동 실행 | P0 |

| FR-1.4 | 환율 자동 적용 (USD → KRW, 1490) | P0 |

#### FR-2: 데이터 정합성

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-2.1 | Upsert 로직: date + source + device + ad_id 기준 중복 방지 | P0 |

| FR-2.3 | 통화 자동 감지 및 환율 적용 | P1 |

#### FR-3: 모니터링 및 알림

| ID | 요구사항 | 우선순위 |
|----|----------|----------|
| FR-3.1 | 백필 시작/완료 텔레그램 알림 | P0 |
| FR-3.2 | 에러 발생 시 즉시 알림 | P0 |
| FR-3.3 | 일일 정합성 검증 결과 알림 | P1 |

### 3.2 비기능 요구사항

| ID | 요구사항 | 목표 |
|----|----------|------|

| NFR-4 | 재시도 로직 | 실패 시 3회 재시도 |

## 4. 시스템 설계

### 4.1 아키텍처

```
┌─────────────────────────────────────────────────────────────────┐
│ GitHub Actions (daily-backfill.yml)                             │
│ - Schedule: 0 18 * * * (UTC) = KST 03:00                       │
└──────────────────────────┬──────────────────────────────────────┘
                           │
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│ 클라이언트별 순차 실행                                           │
│ 1. H.E.A 판교 백필 (backfill-meta-ads.js)                       │
│ 2. 나라똔 백필 (backfill-airtable.js)                           │
└──────────────────────────┬──────────────────────────────────────┘
                           │
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
    ┌──────────┐     ┌──────────┐     ┌──────────┐
    │ Meta API │     │ Supabase │     │ Airtable │
    │ (source) │     │ (clients)│     │ (target) │
    └──────────┘     └──────────┘     └──────────┘
```

### 4.2 백필 스크립트 분류

| 스크립트 | 용도 | 클라이언트 |
|----------|------|------------|
| `backfill-meta-ads.js` | 광고(ad) 레벨 백필 | H.E.A 판교 |
| `backfill-airtable.js` | 캠페인 레벨 백필 | 나라똔 |

### 4.3 데이터 흐름

```
Meta API ──────────────────────────────────────────► Airtable
         │                                            │
         │ date_start      ──────────►  date          │
         │ device_platform ──────────►  device        │
         │ impressions     ──────────►  impressions   │
         │ clicks          ──────────►  clicks        │
         │ spend (USD)     ─── x1490 ►  spend (KRW)   │
         │ actions[lead]   ──────────►  leads         │
         │ video_play_actions ───────►  video_views   │
         │ video_avg_time  ──────────►  avg_watch_time│
         │ ad_id           ──────────►  ad_id         │
         │ campaign_name   ──────────►  campaign_name │
```

## 5. 구현 계획

### 5.1 Phase 1: GitHub Actions 수정 (P0)

1. `daily-backfill.yml` 수정
   - `AIRTABLE_API_KEY` secret 추가
   - 클라이언트별 분리 실행
   - Airtable 백필 스크립트 사용

2. 필요한 GitHub Secrets:
   - `AIRTABLE_API_KEY`
   - `AIRTABLE_HEA_BASE_ID`
   - `AIRTABLE_HEA_TABLE_ID`
   - `AIRTABLE_NARATTON_BASE_ID`
   - `AIRTABLE_NARATTON_TABLE_ID`

### 5.2 Phase 2: 정합성 검증 (P0)

1. 검증 스크립트 작성 (`scripts/verify-backfill.js`)
   - 날짜별 레코드 수 검증
   - 중복 레코드 탐지
   - 환율 적용 검증 (spend 값 범위)

2. 검증 실행 시점:
   - 백필 완료 후 자동 실행
   - 수동 실행 가능

### 5.3 Phase 3: 테스트 코드 (TDD)

1. 단위 테스트:
   - 환율 변환 함수
   - 데이터 변환 함수
   - Upsert 로직

2. 통합 테스트:
   - Meta API mock → Airtable 저장
   - 중복 방지 검증
